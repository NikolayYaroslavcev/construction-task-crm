# Решения и допущения

## Что решил сам там, где ТЗ допускает варианты

**Права и роли**
1. Роль хранится в таблице `profiles`, а не в `user_metadata`: `user_metadata` пользователь может менять сам через API. Политик на изменение `profiles` нет, повысить себе роль нельзя.
2. Постановщики равноправны: любой постановщик видит всё и может принять или вернуть любую задачу, а не только ту, которую создал сам. В ТЗ сказано «видит всё», а при отпуске или замене прораба задачи не должны зависать.
3. Исполнитель в карточке объекта видит только свои задачи на этом объекте, без задач коллег. Так понял требование «видит только свои задачи».
4. Исполнитель видит имена постановщиков (авторов задач и участников истории) и своё имя. Других исполнителей он не видит.

**Задачи и статусы**

5. Смена статуса возможна только через функцию `change_task_status`: прямой UPDATE колонки `status` запрещён правами на колонки, даже постановщику. Матрица переходов существует в одном месте, в базе. Интерфейс повторяет её только для того, чтобы показывать нужные кнопки.
6. Исполнитель у задачи обязателен и должен иметь роль «исполнитель», это проверяет триггер. Задачу без исполнителя создать нельзя.
7. Постановщик может редактировать задачу (название, описание, объект, исполнителя) в любом статусе, в том числе переназначить исполнителя у задачи «В работе». После переназначения задача целиком переходит к новому исполнителю, прежний перестаёт её видеть. Переназначение не является сменой статуса и в историю статусов не пишется.
8. «Принята» считается финальным статусом: из него переходов нет, как и в таблице ТЗ.
9. Комментарий обязателен только при возврате на доработку. Строка из одних пробелов комментарием не считается.
10. Если исполнитель запрашивает чужую задачу, ответ одинаковый: «задача не найдена». Так нельзя даже узнать, что задача существует.
11. Одновременные действия с одной задачей обрабатываются по очереди: функция блокирует строку задачи (`select … for update`), поэтому две смены статуса не наложатся друг на друга.

**Удаление**

12. Объект с задачами удалить нельзя (`on delete restrict`). Сначала нужно удалить или перенести задачи, интерфейс об этом сообщает. Иначе одно неосторожное нажатие стирало бы всю стройку.
13. Удаление задачи не удаляет её историю. Записи остаются в базе как журнал аудита: ссылка на задачу обнуляется, название задачи сохраняется. Такие записи может прочитать только постановщик. Иначе требование «историю нельзя удалить через API» можно было бы обойти удалением задачи.

**Прочее**

14. Тестовые данные создаются скриптом через тот же публичный API, под настоящими пользователями. Поэтому история в демо-данных настоящая, а скрипт заодно проверяет, что разрешённые действия работают.
15. Сверх ТЗ добавлены экран «Все задачи» для постановщика с фильтром по статусам (сразу видно, что ждёт приёмки) и второй постановщик в демо.
16. Сообщения об ошибках из базы переводятся в понятный текст в интерфейсе.

## Что не вошло

- Журнал удалённых задач хранится в базе, но отдельного экрана для него нет: прочитать его можно только через API под постановщиком.
- Переназначение исполнителя и правки задачи не попадают в историю. Сейчас в историю пишутся только смены статуса, как требует ТЗ.
- Нет управления пользователями из интерфейса: сотрудников заводят в панели Supabase, роль назначается SQL-запросом (`supabase/seed.sql`).
- Нет обновления данных в реальном времени: свежие данные подгружаются при открытии страницы и после каждого действия.
- Нет пагинации и поиска. Для десятков задач они не нужны, для тысяч понадобятся.
- Защита от утёкших паролей (проверка по базе HaveIBeenPwned) доступна только на платном тарифе Supabase и не включена.
- Автотесты интерфейса не писал. Логику и безопасность покрывает `npm run security-check`, интерфейс проверен вручную под обеими ролями.
