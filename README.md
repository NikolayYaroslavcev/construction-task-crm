# Стройконтроль: мини-CRM «Объекты и задачи»

Постановщик ставит задачи по объектам (стройкам). Исполнители берут их в работу и сдают на проверку, а постановщик принимает работу или возвращает на доработку. Каждое действие попадает в историю задачи.

Демо: https://construction-task-crm.netlify.app (доступы отправлены вместе с откликом)

- [EXPLANATION.md](EXPLANATION.md): как устроена система, объяснение для руководителя
- [DECISIONS.md](DECISIONS.md): какие решения я принял и почему

## Стек

- Frontend: React 19, TypeScript, Vite, Tailwind CSS 4, shadcn/ui, TanStack Query, React Hook Form + Zod
- Backend: Supabase (PostgreSQL, RLS, SQL-функции и триггеры, Auth, Realtime, Edge Functions)
- Проверки: Vitest, интеграционный тест безопасности против живого API, oxlint, Prettier, GitHub Actions
- Хостинг: Netlify

## Что умеет

| Экран | Постановщик | Исполнитель |
|---|---|---|
| Вход | email и пароль, регистрации нет | то же |
| Объекты | все объекты; создание, изменение, удаление | только объекты, где есть его задачи |
| Карточка объекта | все задачи объекта со статусами, новая задача | только свои задачи на объекте |
| Карточка задачи | данные; «Принять» и «Вернуть на доработку» с обязательным комментарием; правка, переназначение, удаление | данные; «Взять в работу» и «Отправить на проверку» |
| История задачи | смены статусов, переназначения, правки и удаление: кто и когда | то же, по своим задачам |
| Мои задачи | нет | свои задачи, сверху те, что ждут действий |
| Все задачи | все задачи, фильтр по статусу, поиск, журнал удалённых | нет |
| Сотрудники | список и создание учётных записей | нет |

Кнопки в интерфейсе появляются только те, что доступны пользователю в текущем статусе задачи. Изменения приходят в реальном времени: постановщик принял задачу, и у исполнителя статус сменился без перезагрузки. Пароль каждый сотрудник может сменить себе сам.

## Как защищены данные

Правила живут в базе. Интерфейс лишь прячет лишние кнопки, а запрещённый запрос база отклонит, даже если отправить его напрямую.

- RLS включён на всех таблицах, аноним не получает ничего. Исполнитель видит свои задачи и их историю, объекты, где у него есть задачи, своё имя и имена постановщиков.
- Статус меняется только функцией `change_task_status`. У роли `authenticated` есть право UPDATE лишь на `title`, `description`, `object_id` и `assignee_id`, так что напрямую статус не поменять даже постановщику. Функция проверяет, кто её вызвал и разрешён ли переход, блокирует строку (`for update`) и в той же транзакции пишет историю.
- История доступна только для чтения. Прав INSERT, UPDATE и DELETE на `task_status_history` ни у кого нет, записи создают функция смены статуса и триггеры. Если задачу удалить, история останется, а само удаление тоже запишется: кто и когда. Журнал удалённых читает только постановщик.
- Роль хранится в `profiles`, а эту таблицу пользователь изменить не может. В `user_metadata` клиент пишет сам, поэтому роль там не храню. Хелпер `private.is_manager()` лежит в схеме, которой нет в API.
- Id задачи, автора, статус «Новая» и дату создания ставит триггер, присланные клиентом значения игнорируются. Исполнителем назначается только пользователь с ролью «исполнитель».
- Учётные записи создаёт Edge Function `create-user`. Она проверяет, что её вызвал постановщик, а данные валидирует через Zod. Серверный ключ есть только внутри Supabase.
- Регистрация выключена (`enable_signup = false` в [supabase/config.toml](supabase/config.toml)). Во фронтенд попадает только публичный ключ.
- При входе и выходе кэш очищается. На общем компьютере следующий человек не увидит данные предыдущего.

## Проверки

```bash
npm run security-check   # 33 проверки против живого API под исполнителями, постановщиками и анонимом
npm test                 # юнит-тесты матрицы действий (Vitest)
npm run lint             # oxlint
npm run format:check     # Prettier
npm run build            # typecheck и сборка
```

`security-check` сам создаёт тестовый объект и задачи, а потом пытается обойти каждое правило мимо интерфейса. Он читает чужое, меняет статус напрямую, перепрыгивает этапы, подделывает автора и id задачи, дописывает и стирает историю, повышает себе роль, создаёт учётку без прав и пробует зарегистрироваться. После этого проходит разрешённый цикл целиком, с двумя постановщиками, и сверяет каждую запись истории.

GitHub Actions на каждый push проверяет форматирование, линтер, тесты и сборку. Чтобы `security-check` запускался и в CI, нужна переменная `RUN_SECURITY_CHECK=true` и секреты с паролями тестовых пользователей.

## Запуск локально

Понадобятся Node.js 22+ и проект в Supabase, бесплатного тарифа хватает.

```bash
npm install
cp .env.example .env                 # URL проекта, publishable key, пароли тестовых пользователей
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push                 # миграции
npx supabase config push             # выключить открытую регистрацию
npx supabase functions deploy create-user --use-api
```

Первых пользователей заведите в Supabase: Authentication → Users → Add user (Auto Confirm), email берите из `.env`. Потом:

```bash
npx supabase db query --linked -f supabase/seed.sql   # имена и роли
npm run seed                                          # объекты и задачи во всех статусах через API
npm run dev                                           # http://localhost:5173
```

Остальных сотрудников постановщик добавит сам, на экране «Сотрудники».

## Деплой

Netlify собирает сайт из репозитория по настройкам из [netlify.toml](netlify.toml). В переменных окружения сайта задайте `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (публичный ключ).
