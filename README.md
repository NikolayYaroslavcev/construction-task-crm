# Стройконтроль: мини-CRM «Объекты и задачи»

Постановщик ставит задачи по объектам (стройкам), исполнители берут их в работу и сдают на проверку, постановщик принимает работу или возвращает на доработку. Каждое действие попадает в историю задачи.

**Демо:** https://construction-task-crm.netlify.app (доступы переданы вместе с откликом)

- [EXPLANATION.md](EXPLANATION.md): как устроена система, объяснение для руководителя
- [DECISIONS.md](DECISIONS.md): принятые решения

## Стек

- **Frontend:** React 19, TypeScript, Vite, Tailwind CSS 4, shadcn/ui, TanStack Query, React Hook Form + Zod
- **Backend:** Supabase: PostgreSQL, RLS, SQL-функции и триггеры, Auth, Realtime, Edge Functions
- **Качество:** Vitest, интеграционная проверка безопасности против живого API, oxlint, Prettier, GitHub Actions
- **Хостинг:** Netlify

## Возможности

| Экран | Постановщик | Исполнитель |
|---|---|---|
| Вход | email + пароль, регистрация закрыта | то же |
| Объекты | все объекты, создание / изменение / удаление | только объекты, где есть его задачи |
| Карточка объекта | все задачи объекта со статусами, новая задача | только свои задачи на объекте |
| Карточка задачи | данные, «Принять» / «Вернуть на доработку» (с обязательным комментарием), редактирование, переназначение, удаление | данные, «Взять в работу» / «Отправить на проверку» |
| История задачи | смены статусов, переназначения и правки: кто, когда, что | то же по своим задачам |
| Мои задачи | — | свои задачи, сначала то, что ждёт действий |
| Все задачи | все задачи с фильтром по статусам и поиском, журнал удалённых задач | — |
| Сотрудники | список, создание учётных записей | — |

Интерфейс показывает только те действия, которые доступны пользователю в текущем статусе. Изменения приходят в реальном времени: если постановщик принял задачу, у исполнителя статус обновится без перезагрузки. Любой сотрудник может сменить себе пароль.

## Как защищены данные

Все правила находятся в базе. Интерфейс только прячет недоступные кнопки, а база отклоняет запрещённый запрос, даже если отправить его напрямую.

- **RLS на всех таблицах.** Анонимный пользователь не получает ничего. Исполнитель видит только свои задачи, их историю, объекты, где у него есть задачи, своё имя и имена постановщиков.
- **Статус меняет только функция `change_task_status`.** У роли `authenticated` есть право UPDATE только на колонки `title`, `description`, `object_id`, `assignee_id`, поэтому прямой UPDATE статуса невозможен даже для постановщика. Функция проверяет, кто вызывает и разрешён ли переход, блокирует строку (`for update`) и в той же транзакции пишет историю.
- **История только для чтения.** На `task_status_history` нет прав INSERT/UPDATE/DELETE. Записи создают только функция смены статуса и триггеры. Удаление задачи не стирает её историю и само записывается в журнал (кто и когда). Читать журнал удалённых может только постановщик.
- **Роль** хранится в `profiles`, которую пользователь изменить не может (а не в `user_metadata`, которую клиент редактирует сам). Хелпер `private.is_manager()` лежит в схеме, не открытой через API.
- **Автор, статус «Новая» и дата создания** выставляет триггер, значения от клиента игнорируются. Исполнителем можно назначить только пользователя с ролью «исполнитель».
- **Учётные записи** создаёт Edge Function `create-user`: она проверяет, что вызывает постановщик, и валидирует данные через Zod. Серверный ключ существует только внутри Supabase.
- **Регистрация выключена** (`enable_signup = false` в [supabase/config.toml](supabase/config.toml)). Во фронтенд попадает только публичный ключ.
- **Кэш очищается при входе и выходе**, чтобы на общем компьютере следующий пользователь не увидел данные предыдущего.

## Проверки

```bash
npm run security-check   # 33 проверки против живого API под исполнителями, постановщиками и анонимом
npm test                 # юнит-тесты матрицы действий (Vitest)
npm run lint             # oxlint
npm run format:check     # Prettier
npm run build            # typecheck + сборка
```

`security-check` создаёт собственные тестовые объект и задачи и пытается обойти каждое правило в обход интерфейса: прочитать чужое, сменить статус напрямую, перескочить этап, подделать автора или id задачи, дописать или стереть историю, повысить себе роль, создать учётку без прав, зарегистрироваться. Затем он проходит разрешённый цикл от начала до конца с двумя постановщиками и проверяет каждую запись истории.

GitHub Actions на каждый push проверяет форматирование, линтер, тесты и сборку. Запуск `security-check` в CI включается переменной `RUN_SECURITY_CHECK=true` и секретами с паролями тестовых пользователей.

## Запуск локально

Нужны Node.js 22+ и проект в Supabase (бесплатного тарифа достаточно).

```bash
npm install
cp .env.example .env                 # URL проекта, publishable key, пароли тестовых пользователей
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push                 # миграции
npx supabase config push             # выключить открытую регистрацию
npx supabase functions deploy create-user --use-api
```

Первых пользователей создайте в Supabase: Authentication → Users → Add user (Auto Confirm), с email из `.env`. Затем:

```bash
npx supabase db query --linked -f supabase/seed.sql   # имена и роли
npm run seed                                          # объекты и задачи во всех статусах через API
npm run dev                                           # http://localhost:5173
```

Остальных сотрудников постановщик добавляет из интерфейса на экране «Сотрудники».

## Деплой

Netlify собирает сайт из репозитория, настройки лежат в [netlify.toml](netlify.toml). В переменных окружения сайта нужно задать `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (публичный ключ).
